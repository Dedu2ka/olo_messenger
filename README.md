# Olo Messenger: серверная часть

Реактивный бэкенд мессенджера на **Kotlin** и **Spring WebFlux**: авторизация по JWT, доставка сообщений в реальном времени по WebSocket, шифрование данных в базе, push-уведомления через Firebase.

Проект работает в реальной эксплуатации: мессенджером ежедневно пользуются люди из закрытого круга, и он продолжает развиваться. Android-клиент лежит в отдельном репозитории: https://github.com/Dedu2ka/frontend.

## Что умеет

- Регистрация и вход, пароли хранятся как хеш BCrypt.
- Личные чаты, список чатов с последним сообщением и счётчиком непрочитанных.
- Мгновенная доставка по WebSocket, статусы сообщений `SENT` → `DELIVERED` → `READ`.
- Push-уведомления через FCM (необязательная часть: без ключа сервер работает, а push отключён).
- Шифрование текстов сообщений перед записью в PostgreSQL.
- Профиль пользователя и поиск по логину и имени.

## Технические решения

Ниже то, что в проекте было нетривиальным, и как это решено.

| Задача | Решение |
|---|---|
| WebSocket нельзя аутентифицировать заголовком `Authorization` | Клиент получает **одноразовый тикет** (`POST /api/v1/ws-ticket`), который живёт 30 секунд в Redis и удаляется при первом использовании (`GETDEL`). Токен в URL не попадает |
| Как «разлогинить» JWT, который по природе stateless | **Чёрный список в Redis**: токен хранится до конца своего срока жизни (TTL = остаток жизни), затем запись исчезает сама. При выходе открытые WebSocket-сессии пользователя закрываются |
| Повторная отправка сообщения при плохой сети | **Идемпотентность**: клиент присылает `clientMessageId` (UUID), в БД стоит уникальный частичный индекс. Повтор возвращает уже сохранённое сообщение, дубликата нет |
| Два одновременных запроса создают два одинаковых чата или двух пользователей с одним логином | **Advisory-блокировки PostgreSQL** (`pg_advisory_xact_lock`) на время транзакции. Для чата ключ строится из отсортированной пары id, поэтому порядок участников не важен |
| Хранение переписки | **AES-256-GCM**, случайный IV на каждое сообщение, префикс версии `enc:v1:` для будущей смены схемы. При старте сервис досшифровывает старые незашифрованные записи |
| Список чатов без N+1 запросов | Один SQL-запрос с `LATERAL JOIN`: собеседник, последнее сообщение и счётчик непрочитанных (по `last_read_at` участника) |
| Медленный клиент не должен блокировать сервер | У каждого WebSocket-соединения собственный буферизуемый канал (`Sinks.many().unicast().onBackpressureBuffer()`) |
| Сбой внешнего сервиса | Ошибки FCM логируются и не прерывают сохранение и доставку сообщения |

## Архитектура

```
Android-клиент
   │  REST (JWT)            WebSocket (ticket)
   ▼                              ▼
controller ───────────────► websocket
   │                              │
   ▼                              ▼
service  ──────────────────► WebSocketSessionManager
   │            │
   ▼            ▼
repository    PushNotificationService ──► Firebase Cloud Messaging
   │
   ▼
PostgreSQL        Redis (тикеты, чёрный список токенов, кэш профилей)
```

```
messenger-backend/src/main/kotlin/com/example/messenger/
├── controller/   REST-эндпоинты
├── service/      бизнес-логика: чаты, сообщения, доставка, шифрование, push, кэш
├── domain/       сущности и репозитории (Spring Data R2DBC)
├── dto/          объекты ответов
├── security/     JWT, фильтр аутентификации, тикеты, чёрный список
└── websocket/    обработчик соединений и менеджер сессий
```

Схема базы управляется миграциями Flyway (`src/main/resources/db/migration`).

## Стек

Kotlin 2.3 · JDK 21 · Spring Boot 4 (WebFlux, Security, Validation) · Kotlin Coroutines и Project Reactor · PostgreSQL 16 + R2DBC · Flyway · Redis 7 (reactive) · jjwt · Firebase Admin SDK · Docker Compose

## Безопасность

- Секреты (пароль БД, ключ JWT, ключ шифрования) передаются только через переменные окружения. В коде и в репозитории их нет, значений по умолчанию нет, а без них сервер не стартует.
- Любое действие в чате проверяет, что пользователь его участник.
- `userId` из запроса сверяется с пользователем из токена, подменить чужой id нельзя.
- CORS ограничен списком разрешённых источников.

## API (кратко)

| Группа | Эндпоинты |
|---|---|
| Авторизация | `POST /api/v1/auth/register`, `/login`, `/logout` |
| Пользователи | `GET`/`PUT /api/v1/users/me`, `GET /api/v1/users/search` |
| Чаты | `POST /api/v1/chats/direct`, `GET /api/v1/chats`, `POST /api/v1/chats/{id}/read` |
| Сообщения | `GET`/`POST /api/v1/chats/{id}/messages`, `POST /api/v1/chats/direct/messages` |
| Realtime | `POST /api/v1/ws-ticket`, затем `ws://host:8080/ws?ticket=...` |
| Push | `POST`/`DELETE /api/v1/notifications/device-token` |

События WebSocket: `NEW_MESSAGE`, `MESSAGE_STATUS`, `ERROR`.

## Запуск

Нужны JDK 21 и Docker.

```bash
cd messenger-backend
cp .env.example .env        # заполнить значения, подсказки внутри файла
./gradlew clean bootJar
docker compose up --build -d
```

Сервер будет доступен на `http://localhost:8080`. Push-уведомления включаются отдельно, см. [PUSH_NOTIFICATIONS_SETUP.md](messenger-backend/PUSH_NOTIFICATIONS_SETUP.md).

## Планы развития

Проект развивается, ближайшие улучшения:

- **Групповые чаты.** Сейчас поддерживаются личные диалоги, модель данных (`chats.type`, `chat_members`) уже рассчитана на расширение.
- **Горизонтальное масштабирование.** Перенос рассылки WebSocket-событий между узлами на Redis Pub/Sub: сейчас сессии хранятся в памяти одного экземпляра.
- **Refresh-токены.** Короткоживущий access-токен вместо одного токена на 24 часа.
- **Постраничная загрузка истории** сообщений вместо выдачи целиком.
- **Ограничение частоты запросов** на вход и отправку сообщений.
- **Автотесты.** Модульные тесты сервисного слоя и интеграционные сценарии на Testcontainers.
